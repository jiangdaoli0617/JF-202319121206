# 05 开发规范与模板

> 本文档中的模板均为**最小可用版本**，随用随取。若某项约束在实践中被证明无价值，
> 直接删除对应段落即可，不要为了「保持文档完整」而保留无用规则。

## 1. 命名规范

| 对象 | 规则 | 示例 |
|------|------|------|
| 目录 | 小写，不用中文 | `bsp/`、`middle/`、`app/` |
| C 文件 | `<层>_<模块>.c/h` | `bsp_rc522.c`、`drv_net.c`、`app_fsm.c` |
| C 函数 | 小写下划线，前缀为层与模块 | `bsp_rc522_write_reg()`、`app_log_push()` |
| C 全局变量 | `g_` 前缀 + 小写下划线 | `g_sys_config`、`g_net_state` |
| C 宏 / 枚举 | 全大写 | `RFID_UID_LEN`、`ST_IDLE` |
| Java 类 | 大驼峰 | `TcpSession`、`LogService` |
| Java 方法/变量 | 小驼峰 | `saveIfAbsent()`、`equipId` |
| JS 文件 | 小写，短横线或单模块 | `ws.js`、`config.js` |

**统一原则**：文件名即分层标识。看到 `bsp_` 就知道它在驱动层，可以碰寄存器；
看到 `app_` 就知道它不该出现任何 `HAL_` 或 `SPI_` 调用。

## 2. 文件头注释模板

**C 文件（.c 与 .h 相同）**
```c
/**
 * @file    bsp_rc522.c
 * @brief   RC522 射频读卡驱动（SPI1）
 * @note    引脚：SCK=PA5 MISO=PA6 MOSI=PA7 NSS=PA4 RST=PB0
 */
```

**Java 类**
```java
/**
 * 单条 TCP 连接的处理：字节流拆帧、分发、回 ACK。
 * 每个 STM32 连接对应一个实例。
 */
```

**规则**：只写「文件做什么」和「不写会踩坑的信息」（引脚、地址、约束）。
不写作者、日期、版本号——这些由 Git 记录，写进注释只会随代码变化而失效。

## 3. 函数注释模板

仅在**接口文件（.h）**和**公开方法**上写，`.c` 内部静态函数不写。

```c
/**
 * @brief  从队列取一条日志并发送
 * @param  e  待入队的日志记录
 * @retval 1  入队成功
 * @retval 0  队列已满
 */
uint8_t app_log_push(const log_entry_t *e);
```

Java 用最简 Javadoc，只在返回值含义非显然时补充：
```java
/** @return true 表示新记录，false 表示重复 seq 被忽略 */
boolean saveIfAbsent(LogRecord r);
```

## 4. Git 提交规范

**格式**
```
<类型>(<范围>): <描述>

<可选：为什么这么改，仅当描述本身不足以说明时>
```

**类型**

| 类型 | 用途 |
|------|------|
| `feat` | 新增功能 |
| `fix` | 修复缺陷 |
| `docs` | 文档变更 |
| `refactor` | 重构，行为不变 |
| `proto` | 通信协议变更（**必须同步两端**） |
| `iface` | 模块接口变更 |
| `test` | 测试相关 |
| `chore` | 构建、配置、依赖 |

**范围**：`docs` / `firmware` / `server` / `web` / `hardware`

**示例**
```
feat(firmware): 新增 RC522 读卡驱动
fix(firmware): 修复 I2C 总线在多从机下的时钟拉伸超时
proto: 新增 EQUIP_NAME 字段(Tag 0x08)
docs(03): 补充 ESP8266 供电去耦要求
```

**粒度要求**：一次提交只做一件事。改驱动的提交里不要夹带界面改动——
这样出问题时 `git revert` 才能干净地回退。

## 5. 分支与版本

**分支策略（个人项目简化版）**

```
main          始终可编译、可演示。不直接在上面写半成品
 └── dev      日常开发
      └── feature/xxx   单个模块或较大改动
```

- 小改动（改注释、修错别字）可直接提交到 `dev`。
- 一个完整模块完成后，`dev` → `main` 合并，并打 tag。
- 出问题时从 tag 回退，不在 `main` 上反复试错。

**里程碑 tag**

| tag | 含义 |
|-----|------|
| `v0.1-docs` | 设计文档定稿 |
| `v0.2-bsp` | 驱动层跑通（读卡/时钟/存储/显示分别验证） |
| `v0.3-firmware` | 业务逻辑 + 协议层跑通 |
| `v0.4-server` | Java 后端可收数据并落库 |
| `v0.5-web` | 前端可查看台账与日志 |
| `v1.0-release` | 全链路联调通过，可答辩演示 |

## 6. 新增一个模块的标准流程

按此顺序做，可避免返工。以「新增 RFID 模块」为例：

1. 在 `docs/04` 中补上该模块的接口定义。
2. `git checkout -b feature/rc522` 开分支。
3. 写 `bsp_rc522.c/h`，**单独写一个测试函数验证能读出卡号**，不要急着接业务。
4. 写 `middle/drv_rfid.c/h` 包装成抽象接口。
5. 在 `main.c` 中调用，验证 `drv_rfid_poll()` 返回正确。
6. 通过后合入 `dev`，提交 `feat(firmware): 新增 RC522 读卡驱动`。
7. 删除分支。

**核心要求**：每一步都要能独立验证。写驱动时业务还没接，就要能用串口打印卡号；
写业务时驱动已经稳定。**绝不允许「全部写完再一起调」**——那样出问题时无法定位是哪一层。

## 7. 调试输出规范

串口调试信息统一格式，便于用工具过滤：

```c
#define LOG_TAG_BSP   "BSP"
#define LOG_TAG_APP   "APP"
#define LOG_TAG_PROTO "PROTO"

LOGI(LOG_TAG_BSP, "rc522 version=0x%02X", ver);     /* 正常信息 */
LOGW(LOG_TAG_PROTO, "crc fail, len=%d", len);       /* 警告 */
LOGE(LOG_TAG_APP, "log queue full");                /* 错误 */
```

输出形如 `[BSP] rc522 version=0x12`。另一路调试串口应预留关闭开关
（`#define DEBUG_UART_EN 0`），正式演示时关闭以免影响时序。

## 8. 文档模板

新增设计文档时用此骨架，无内容的章节直接删掉，不留空标题：

```markdown
# 0X 文档标题

## 1. 目的
（这份文档解决什么问题，谁来看）

## 2. 设计
（正文）

## 3. 接口 / 约定
（若无可删）

## 4. 待确认
（若有未决事项）
```

## 9. 提交前检查清单

- [ ] 能编译通过（Keil 无 error、Maven 无 error）
- [ ] 新增的代码放在了正确的层（`app/` 里没有 `bsp_` 调用）
- [ ] 接口有变动时，`docs/02` 或 `docs/04` 已同步更新
- [ ] 跨端改动在同一个 commit 内
- [ ] commit message 符合第 4 节格式
- [ ] 没有把 `Objects/`、`target/`、`unpackage/` 等生成物提交进来
