# 02 系统架构与通信协议

本文档是上下位机之间的**契约**。STM32 端与 Java 端的编解码实现必须严格对照本文，
任何一方修改协议都必须先改本文并同步另一方。

## 1. 分层架构

```
┌──────────────── 现场端 STM32F103 ────────────────┐
│  bsp 层     RC522 / DS3231 / AT24C02 / OLED /    │  直接操作寄存器与外设
│             按键 / 声光 / ESP8266                │
├──────────────────────────────────────────────────┤
│  middle 层  drv_rfid / drv_rtc / drv_storage /   │  统一抽象接口
│             drv_display / drv_net               │
├──────────────────────────────────────────────────┤
│  app 层     app_fsm / app_auth / app_inventory / │  纯业务，不碰硬件
│             app_log / app_ui                    │
├──────────────────────────────────────────────────┤
│  protocol   proto_frame / proto_tlv / proto_crc  │  协议编解码
└──────────────────────────────────────────────────┘
                        │ USART2
                 ┌──────┴──────┐
                 │ ESP8266-01S │
                 └──────┬──────┘
                        │ TCP（局域网）
┌───────────────────────┴──────────────────────────┐
│  Java 后端                                        │
│   net.TcpServer ──► protocol.* ──► service.* ──►  │
│                                    dao.* (SQLite) │
│                              └──► net.WsServer    │
└───────────────────────┬──────────────────────────┘
                        │ WebSocket
              ┌─────────┴──────────┐
              │ uni-app 前端        │
              └────────────────────┘
```

**依赖方向**：`app → middle → bsp`，`protocol` 被 `app` 与 `net` 共同依赖但自身不依赖任何层。
跨层反向调用一律禁止。业务层只 include `drv_*.h`，从不 include `bsp_*.h`。

## 2. 传输层参数

| 项 | 值 |
|----|-----|
| 物理层 | ESP8266-01S，AT 固件，WiFi STA 模式 |
| 传输层 | TCP，Java 端为 Server，STM32 端为 Client |
| 服务器端口 | 9000（TCP 数据） / 9001（WebSocket 前端） |
| 串口参数 | USART2，115200-8-N-1 |
| 字节序 | **大端（网络序）**，全协议统一 |
| 字符编码 | UTF-8 |
| 最大帧长 | 256 字节（STM32 侧接收缓冲限制） |

### 2.1 设备维度（多终端）

一个实验室可部署多台终端，每台以 `DEVICE_ID` 唯一标识（如 `LAB-01-A`、`LAB-01-B`）。
终端之间**分区管理**，同一件器材只归属一台终端，因此协议中**不为每条记录附加设备号**，
设备身份由连接上下文确定：

| 环节 | 设备维度的体现 |
|------|---------------|
| 连接绑定 | 收到首个 `BOOT_NOTIFY` 或 `HEARTBEAT` 后，Java 将该连接绑定到对应 `DEVICE_ID` |
| 档案下发 | Java 按连接的 `DEVICE_ID` 过滤，只下发该终端所属的器材 |
| 卡表下发 | 身份卡名单全实验室共享，下发给所有在线终端，用于离线权限校验 |
| 新增器材 | 默认归属发起操作的终端；上位机可在界面上改归属 |
| 日志上报 | 来源终端由连接上下文确定，不占用额外 Tag，节省帧长 |
| 状态推送 | WebSocket 可按终端过滤，前端可只看某台终端的数据 |
| 冲突处理 | 分区保证器材不重叠，**不存在跨终端并发借还**，无需服务端仲裁 |

## 3. 帧格式

```
 0        2      3      4        6              8+N      10+N
 ┌────────┬──────┬──────┬────────┬──────────────┬────────┐
 │ 帧头    │ 版本 │ 类型 │ 序号    │   载荷        │ CRC16  │
 │ AA 55  │ 0x01 │      │  u16   │   TLV 列表    │  u16   │
 └────────┴──────┴──────┴────────┴──────────────┴────────┘
   2 字节          1      1       2       N          2
```

| 偏移 | 字段 | 长度 | 说明 |
|------|------|------|------|
| 0 | 帧头 | 2 | 固定 `0xAA 0x55` |
| 2 | 版本 | 1 | 协议版本，当前 `0x01` |
| 3 | 类型 | 1 | 消息类型，见第 5 节 |
| 4 | 序号 | 2 | 大端，发送方自增，用于 ACK 匹配 |
| 6 | 长度 | 2 | 大端，**载荷**字节数，不含帧头与 CRC |
| 8 | 载荷 | N | TLV 列表，可为空（N=0） |
| 8+N | CRC16 | 2 | 大端，CRC16-MODBUS，覆盖偏移 2 ~ 8+N-1 |

固定头总长 10 字节。接收方按「找帧头 → 读长度 → 收满 → 校验 CRC」的流程解析；
校验失败则丢弃并回移一字节重新找帧头，避免因假帧头导致长时间失步。

## 4. 载荷编码：TLV

载荷由若干 TLV 单元顺序拼接，格式 `Tag(1) + Len(1) + Value(Len)`。

**这是协议可扩展性的核心**：接收方遇到不认识的 Tag，因 Len 已知，直接跳过即可继续解析后续
字段。因此新增业务字段只需分配新 Tag，**收发两端的解析代码无需改动，版本号也无需变更**。

### 4.1 Tag 分配表

| Tag | 名称 | 类型 | 长度 | 说明 |
|-----|------|------|------|------|
| `0x01` | DEVICE_ID | string | 变长 | 设备标识，如 `LAB-01-A` |
| `0x02` | TIMESTAMP | uint32 | 4 | Unix 秒（UTC） |
| `0x03` | EQUIP_ID | uint16 | 2 | 器材编号 |
| `0x04` | USER_CARD | uint32 | 4 | 操作人卡号（UID） |
| `0x05` | OP_TYPE | uint8 | 1 | 操作类型，见 4.2 |
| `0x06` | RESULT | uint8 | 1 | 结果码，见 4.3 |
| `0x07` | STOCK_COUNT | uint16 | 2 | 当前在库数量 |
| `0x08` | EQUIP_NAME | string | 变长 | 器材名称 |
| `0x09` | LOG_SEQ | uint32 | 4 | 日志全局序号，用于去重与补传定位 |
| `0x0A` | CARD_UID | uint32 | 4 | 被读到的原始卡号（异常场景用） |
| `0x0B` | EQUIP_STATUS | uint8 | 1 | 器材状态，见 4.4 |
| `0x0C` | USER_NAME | string | 变长 | 操作人姓名 |
| `0x0D` | DUE_TIME | uint32 | 4 | 应归还时间（Unix 秒） |
| `0x0E` | ERROR_MSG | string | 变长 | 错误描述 |
| `0x0F` | TOTAL | uint16 | 2 | 分片总数 |
| `0x10` | INDEX | uint16 | 2 | 分片序号，从 1 开始 |
| `0x11` | RECORD_COUNT | uint16 | 2 | 本帧携带的记录条数 |
| `0x12` | USER_ROLE | uint8 | 1 | `0x01` 管理员，`0x02` 学生 |
| `0x13`~`0x6F` | — | — | — | **预留给后续扩展** |
| `0x70`~`0x7E` | — | — | — | 实验性字段，不保证兼容 |
| `0x7F` | RESERVED | — | — | 占位 |

### 4.2 OP_TYPE 取值

| 值 | 含义 |
|----|------|
| `0x01` | 借出 |
| `0x02` | 归还 |
| `0x03` | 入库登记 |
| `0x04` | 删除/停用 |
| `0x05` | 手动登记 |
| `0x06` | 系统事件（上电、联网、对时） |
| `0x07` | 异常 |
| `0x08` | 超期提醒 |

### 4.3 RESULT 取值

| 值 | 含义 |
|----|------|
| `0x00` | 成功 |
| `0x01` | 未授权卡片 |
| `0x02` | 未登记器材 |
| `0x03` | 器材已借出 |
| `0x04` | 器材未被借出 |
| `0x05` | 操作超时 |
| `0x06` | 重复刷卡（已去重） |
| `0x07` | 内部错误 |

### 4.4 EQUIP_STATUS 取值

与 `01-需求说明书.md` 第 3 节一致：`0x00` 在库、`0x01` 已借出、`0x02` 超期、
`0x03` 未登记、`0x04` 已停用。

## 5. 消息类型

| 类型 | 方向 | 名称 | 载荷 | 说明 |
|------|------|------|------|------|
| `0x01` | ↑ | HEARTBEAT | DEVICE_ID, TIMESTAMP, STOCK_COUNT | 每 30 s 一次 |
| `0x02` | ↑ | LOG_REPORT | LOG_SEQ, OP_TYPE, EQUIP_ID, USER_CARD, TIMESTAMP, RESULT, [EQUIP_NAME], [DUE_TIME] | 业务日志上报 |
| `0x03` | ↑ | ARCHIVE_REQ | DEVICE_ID | 上电时请求全量档案 |
| `0x04` | ↑ | ARCHIVE_CHANGE | OP_TYPE, EQUIP_ID, [EQUIP_NAME], EQUIP_STATUS | 管理员增删器材后上报 |
| `0x05` | ↑ | BOOT_NOTIFY | DEVICE_ID, TIMESTAMP | 上电通知，上位机据此触发对时、档案与卡表下发 |
| `0x06` | ↑ | USER_REQ | DEVICE_ID | 请求全量身份卡名单（手动重同步时用） |
| `0x10` | ↓ | TIME_SYNC | TIMESTAMP | 下发标准时间 |
| `0x11` | ↓ | ARCHIVE_DATA | TOTAL, INDEX, RECORD_COUNT, (EQUIP_ID, EQUIP_NAME, EQUIP_STATUS)×N | 档案下发，可分片 |
| `0x12` | ↓ | ARCHIVE_ACK | — | 档案下发完成确认 |
| `0x13` | ↓ | USER_DATA | TOTAL, INDEX, RECORD_COUNT, (USER_CARD, USER_ROLE)×N | 身份卡名单下发，可分片 |
| `0x80` | ↓ | ACK | RESULT | 对 `0x02` 的确认，序号与上报帧一致 |
| `0x81` | ↑ | ACK_RESP | RESULT | STM32 对下行帧的确认 |
| `0xFF` | 双向 | ERROR | RESULT, [ERROR_MSG] | 错误应答 |

箭头方向以 STM32 为视角：`↑` 表示 STM32 → Java，`↓` 表示 Java → STM32。

> **超期事件复用 `LOG_REPORT`**，不新增消息类型：以 `OP_TYPE=0x08` 上报，
> 载荷携带 `EQUIP_ID`、`USER_CARD`、`DUE_TIME`、`RESULT=0x00`。
> 同一器材在一次借出周期内只上报一次，归还后重置。
> 这样上位机只需一套入库逻辑，避免为每种事件各写一条处理路径。

> 接收方遇到未知类型值，应回一条 `0xFF`（RESULT=`0x07`）并忽略该帧，
> 不得断开连接。这保证了下位机固件比上位机新（或反之）时系统仍可降级运行。

## 6. 可靠性机制

### 6.1 日志上报与确认（停等协议）

STM32 侧维护一个日志环形队列，**容量 36 条，落盘于 EEPROM**（见 `07-EEPROM存储设计.md`）。
发送流程：

```
取队首记录 → 沿用其 LOG_SEQ → 发送 LOG_REPORT → 启动 3 s 超时定时器
   │
   ├─ 收到 ACK（序号匹配） ──► EEPROM read_ptr 前进一格 ──► 出队 ──► 发下一条
   ├─ 超时未收到 ──► 重试，最多 3 次 ──► 仍失败则保留在队列，等待网络恢复
   └─ 队列中还有记录 ──► 间隔 200 ms 发下一条
```

记录在**产生时即写入 EEPROM**，并在向用户显示「成功」前完成落盘，因此断电不丢。
ACK 只是把读指针前移，被确认的槽位随后可被新记录覆盖。
队列满时拒绝新的借还操作并提示联网，**不覆盖最旧记录**。

LOG_SEQ 由 STM32 维护并持久化，掉电重启后从上次值 +1 继续，**上位机以此字段做幂等判重**，
因此重复上报不会产生重复记录。

### 6.2 断线检测与重连

| 事件 | 检测方式 | 动作 |
|------|---------|------|
| 链路断开 | 心跳连续 3 次未收到 ACK | 关闭 Socket，回到 `IDLE`，LED 慢闪 |
| 重连 | 每 10 s 尝试一次 `AT+CIPSTART` | 成功后发送 `BOOT_NOTIFY` 触发对时与档案同步 |
| 补传 | 重连成功且队列非空 | 把 EEPROM 中未确认的记录按 LOG_SEQ 升序逐条补发 |

心跳同时承担「保活」作用，防止 NAT/AP 因空闲回收连接。

**档案同步与本地未确认操作的冲突**：终端重连后会收到服务端下发的全量档案，其中不包含
断网期间在本地完成的借还。终端必须**先应用服务端档案，再按 `LOG_SEQ` 顺序重放本地未确认的
借出/归还日志**（赋值式，幂等），然后落盘。否则本地状态会被旧档案覆盖，出现
「器材显示在库、实际已被借走」。若重放时发现器材已被服务端停用，则跳过重放并记录一条异常。

### 6.3 时间同步

STM32 无网络时钟源，DS3231 长期运行会有累计误差。

- **触发时机**：上电联网后、每 6 小时、收到 `TIME_SYNC` 时
- **方向**：Java → STM32 单向下发（Java 侧作为时间权威）
- **写入**：若与本地时间偏差 > 2 s 才写入 DS3231，避免频繁写寄存器
- **多终端**：每台终端独立对时，互不依赖；某台离线不影响其他终端的时间准确性

### 6.4 去重（针对难点 4）

两级去重，任一级命中都按「重复刷卡」处理并记录 `RESULT=0x06`：

1. **硬件级**：RC522 连续读到相同 UID 且间隔 < 2 s → 视为同一次刷卡，不上报。
2. **协议级**：上位机按 `LOG_SEQ` 幂等判重，重复的 `LOG_REPORT` 直接回 ACK 但不入库。

### 6.5 超期扫描与上报

超期判定在终端本地完成（详见 `01-需求说明书.md` 4.5 节），不依赖服务端：

- 每 60 s 扫描一次本地档案，状态为 `LENT` 且 `now > due_time` 的器材进入超期。
- 首次进入超期时上报一条 `LOG_REPORT`（`OP_TYPE=0x08`），同一借出周期内不重复上报。
- 上报同样走停等确认；断网时先入队，联网后补传，保证超期记录不丢。
- 上位机可按 `DUE_TIME` 独立再算一次超期，作为交叉校验。

超期只是提示性状态，不触发额外的锁定逻辑；归还流程与正常归还完全一致，
归还后超期标记清除。

## 7. 典型交互时序

### 7.1 上电

```
STM32                                Java 后端
  │ 外设自检 → 读配置/卡表/档案/日志(EEPROM) │
  │──── TCP 连接建立 ──────────────────►│
  │──── BOOT_NOTIFY(DEVICE_ID, T) ─────►│
  │◄─── TIME_SYNC(T') ─────────────────│  写入 DS3231
  │──── ACK_RESP(0x00) ───────────────►│
  │◄─── ARCHIVE_DATA(1/1, N 条) ───────│
  │──── ACK_RESP(0x00) ───────────────►│
  │◄─── ARCHIVE_ACK ───────────────────│
  │◄─── USER_DATA(1/1, M 张卡) ────────│  身份卡名单，存 EEPROM
  │──── ACK_RESP(0x00) ───────────────►│
  │──── HEARTBEAT ────────────────────►│  此后每 30 s
  │◄─── ACK ──────────────────────────│
```

> `ARCHIVE_DATA` 只包含归属该终端 `DEVICE_ID` 的器材；心跳中的 `STOCK_COUNT`
> 也仅统计该终端辖区，便于前端按终端分别展示。`USER_DATA` 为全实验室共享的卡表，
> 每个终端收到相同内容。
>
> 上电恢复在联网**之前**完成。即使网络完全不可用，终端也能凭 EEPROM 中的档案与卡表
> 进入待机并接受借还，日志先存入本地队列，联网后再补传。

### 7.2 一次借出

```
刷学生卡 → 状态机进入 AUTH_OK → 刷器材卡 → 校验通过
  │
  │ 本地：更新器材状态为 LENT、OLED 显示、绿灯短鸣、写 DS3231 时间戳
  │
  │──── LOG_REPORT(OP_TYPE=0x01, EQUIP_ID, USER_CARD, T, RESULT=0x00) ──►│
  │◄─── ACK(0x00) ────────────────────────────────────────────────────│
  │ 记录出队，Java 侧入库并 WebSocket 推送到前端
```

## 8. 协议版本演进规则

1. **加字段** → 新 Tag，不改版本号。这是绝大多数变更的形态。
2. **加功能** → 新消息类型，不改版本号。旧端收到未知类型回 `0xFF` 并忽略。
3. **改既有字段语义或长度** → 必须升版本号，并在两端同时实现双版本兼容分支。
4. **废弃字段** → 保留 Tag 定义但不再发送，至少保留两个版本后再回收。

> 该规则的目的是把「上下位机必须同步升级」的场景压缩到最少。日常开发中绝大多数改动
> 都属于第 1、2 类，因此两端可以独立迭代。

## 9. 前端（WebSocket）接口

Java 后端对前端使用 JSON 文本帧，结构与协议解耦（前端不感知 TLV）：

```json
{ "type": "log",        "data": { "seq": 1024, "opType": "LEND", "equipId": 17,
                                  "equipName": "示波器", "userCard": "0x1A2B3C4D",
                                  "userName": "张三", "timestamp": 1758960000,
                                  "result": "OK" } }
{ "type": "status",     "data": { "online": true, "stockCount": 42, "deviceId": "LAB-01" } }
{ "type": "equipment",  "data": { ... } }
{ "type": "equipList",  "data": [ ... ] }
```

前端仅依赖 `type` 字段分发。新增业务类型时前端加一个 switch 分支即可，
既有分支不受影响。
