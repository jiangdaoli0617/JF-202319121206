# 06 技术难点与对策

本文档逐条回应原始需求中列出的 7 项难点，并补充 3 项在实际设计中识别出的新风险。
每项给出**成因 → 对策 → 验证方式**，验证方式是答辩时的实测素材。

## 难点 1：RFID 受金属与电磁干扰，漏读、误读、识别不稳

**成因**：13.56MHz 磁场在金属表面产生涡流，抵消天线磁场，导致读距骤降；
实验室的示波器、电源、电机等本身就是强干扰源。

**对策**

| 层面 | 措施 |
|------|------|
| 布置 | 天线面与金属保持 ≥ 10 mm，中间垫铁氧体隔磁片 |
| 标签 | 金属器材改用抗金属标签（带隔离层的特种标签） |
| 软件 | 连续 3 次读同一 UID 才认定为有效卡，滤掉单次误读 |
| 软件 | 读卡失败自动重试 3 次，间隔 50 ms |
| 软件 | 天线增益调至最大（`RC522` 的 `RFCfgReg` 寄存器） |

**验证方式**：分别在「无遮挡」「贴金属」「距金属 1 cm」三种条件下各刷 50 次，
统计成功率并记录读距。这组数据可直接写进论文的测试章节。

## 难点 2：多总线并发导致时序冲突与程序卡顿

**成因**：SPI、I2C、USART 三条总线若在中断里互相等待，或某处使用阻塞延时，
会互相拖死。典型症状是刷卡时屏幕卡住、或联网时按键无响应。

**对策**

1. **全流程非阻塞**：主循环内所有 `*_poll()` 不得有 `delay_ms()`。
   需要「等待 15 秒」这类逻辑，用「记录起始时间戳 + 每次循环比对」实现。
2. **中断只做搬运**：USART 中断里只往环形缓冲塞字节，解析在主循环做。
   中断里绝不做 SPI 或 I2C 操作——这是最容易踩的坑。
3. **总线访问串行化**：同一时刻只允许一个模块使用 I2C1。
   本设计的 I2C 从机（DS3231/AT24C02/OLED）访问都很快，天然错开即可；
   若出现竞争，加一个 `i2c_bus_lock()` 软件锁。
4. **优先级安排**：USART 中断优先级高于其他，保证联网响应；
   但不可设为最高，需为系统滴答留出空间。
5. **OLED 局部刷新**：只刷新变化的行，避免整屏刷新拖慢主循环。

**验证方式**：连续运行 72 小时，期间反复刷卡、按键、断开重连网络，
用串口打印主循环单次执行耗时，确认稳定在毫秒级且无累积增长。

## 难点 3：EEPROM 频繁读写导致数据错乱或丢失

**成因**：AT24C02 只有 2KB 且擦写寿命约 100 万次。若把每次借还日志都写进 EEPROM，
既写不下，几万次操作后还会出现坏块；且写入过程中断电会留下半截数据。

**对策（本质是改变用法，而非加保护）**

1. **不使用 EEPROM 承载日志**。EEPROM 只保存系统配置（约 200 字节），
   写入频率从「每次操作」降到「配置变更时」，寿命问题自动消失。
2. **日志走上报 + 确认**。未确认的记录驻留 RAM 队列，联网后补传。
   断网期间靠 RAM 缓冲（64 条），足够覆盖绝大多数场景。
3. **双备份 + 校验和**。配置区写两份，各带校验和。读取时校验；
   主份损坏则回滚到备份份，两份都坏则恢复出厂值并报警。
4. **写入原子性**。写配置时先写备份区、再写主区，
   任一步断电都至少有一份完整数据。
5. **页边界对齐**。AT24C02 页大小 8 字节，跨页写必须分两次，
   否则地址会在页内回卷覆盖数据——这是最常见的 EEPROM 数据错乱原因。

**验证方式**：写入过程中断电 20 次，检查每次重启后配置是否可读且正确；
连续写入 1 万次后校验数据完整性。

## 难点 4：重复刷卡、空白卡、未授权卡的异常过滤

**成因**：用户刷卡动作不是瞬时的，卡在感应区停留数百毫秒会触发连续多次读卡；
空白卡（未写入的 Mifare 卡）也能被读出 UID；未登记的卡随处可得。

**对策**：分三级过滤，每级对应一个明确的处理动作。

| 级别 | 场景 | 判据 | 处理 |
|------|------|------|------|
| 硬件级 | 重复刷卡 | 同一 UID，距上次 < 2 s | 静默忽略，不响应、不上报 |
| 逻辑级 | 空白卡 / 无效卡 | UID 为全 0 或读取 CRC 校验失败 | 红长鸣，提示「无效卡片」 |
| 业务级 | 未授权卡 | UID 不在身份卡表中 | 红长鸣，提示「未授权」，**上报异常日志** |
| 业务级 | 未登记器材 | UID 不在器材档案中 | 红长鸣，提示「未登记」，**上报异常日志** |
| 协议级 | 重复上报 | 同一 `LOG_SEQ` 二次到达 | 上位机回 ACK 但不重复入库 |

**设计要点**：硬件级去重必须在**上报之前**完成。若把重复刷卡也上报，
上位机日志会被刷屏，真正的异常反而被淹没。

**验证方式**：卡在感应区停留 5 秒，确认只产生 1 条记录；
用空白卡、未授权卡各刷 10 次，确认每次都正确报错且异常日志条数正确。

## 难点 5：借出、归还、超期的状态判断与时序切换

**成因**：一次操作跨越两次刷卡和一个 15 秒窗口，中间可能插入超时、中途放弃、
重复刷同一张卡等情况，状态容易错乱。

**对策**

1. **显式状态机**（见 `01-需求说明书.md` 4.4 节）。所有状态迁移集中在 `app_fsm.c`
   一个 `switch` 里，任何时刻系统只处于一个确定状态，避免散落各处的标志位互相打架。
2. **状态迁移表**。把「当前状态 + 事件 → 新状态 + 动作」列成表再写代码，
   比直接写 `if-else` 更不容易漏分支。
3. **超时统一管理**。`AUTH_OK` 和 `ADMIN_MENU` 两个状态各有一个超时计时器，
   由主循环统一检查，不用定时器中断（避免中断与主循环共享状态）。
4. **状态变更即落日志**。每次器材状态变化都调用 `app_log_push()`，
   保证日志与状态严格对应，事后可完整重建任意时刻的库存情况。
5. **超期用衍生计算**，不存独立状态。`OVERDUE` 由 `now > due_time` 实时判断，
   避免出现「状态说是超期但时间已经归还」这类不一致。

**验证方式**：构造边界场景——刷卡后立刻走开（超时）、中途刷另一张身份卡、
归还从未借出的器材、连续借还同一器材。逐条确认状态与日志正确。

## 难点 6：ESP8266 联网不稳，断连与丢包

**成因**：WiFi 信号波动、AP 空闲回收连接、ESP8266 供电不足瞬时复位、
AT 指令响应超时。这四类原因表象相似，需要区分对待。

**对策**

| 原因 | 表现 | 对策 |
|------|------|------|
| 供电不足 | 联网瞬间整机复位 | 3.3V 电源 ≥ 500 mA，就近加 100 µF 去耦（见 `03` 第 4 节） |
| 空闲被回收 | 静置一段时间后连接消失 | 30 s 心跳保活 |
| 信号波动 | 随机断连 | 心跳连续 3 次无 ACK 判定断线，10 s 后重连 |
| 丢包 | 数据发了但上位机没收到 | 停等协议 + 3 s 超时重传，最多 3 次 |
| 指令超时 | AT 无响应 | 每条 AT 指令带 2 s 超时，超时后重发并计数 |

**关键设计：断线不丢数据。** 记录在发出并被 ACK 确认前不离开队列，
因此断连只是延迟上传，不会丢失。重连成功后按 `LOG_SEQ` 升序补传，
上位机按 seq 幂等判重，即使重复发送也不会产生重复记录。

**验证方式**：借还 5 次后人为断开 WiFi（关掉路由器或拔掉 ESP8266 电源），
再借还 5 次，恢复网络后检查上位机是否完整收到 10 条记录、有无重复。

## 难点 7：Java 端 Socket 通信与数据同步

**成因**：TCP 是字节流，不保证「一次 recv 对应一帧」，必须自己处理粘包与半包；
多客户端并发时还有线程安全问题。

**对策**

1. **粘包/半包处理**。接收侧维护一个累积缓冲区，
   按「找帧头 `AA 55` → 读长度字段 → 判断是否收满 → 校验 CRC」循环取帧，
   取不完整的部分留在缓冲区等下次数据。**绝不能假设一次 `read()` 就是一帧。**
2. **每连接一线程**。STM32 数量少（通常 1 台），用最简单的「一连接一线程」模型即可，
   不引入 NIO 增加复杂度。线程内串行处理该连接的所有帧，天然避免并发问题。
3. **共享数据加锁**。器材台账与日志列表被 TCP 线程写、被 WebSocket 线程读，
   用 `ConcurrentHashMap` 或对 DAO 方法加 `synchronized`。
4. **幂等入库**。`LOG_SEQ` 建唯一索引，重复 seq 插入时忽略。
   这是应对重传的最后一道防线。
5. **分层解耦**。`service` 层不感知 Socket，`dao` 层不感知协议，
   将来换成 HTTP 接口或换数据库都不影响业务代码（见 `04` 第 3.3 节）。

**验证方式**：用工具模拟发送「半个帧 + 延迟 + 另外半个帧」，
确认能正确拼出完整帧；用脚本重复发送同一 seq 的记录，确认数据库只有一条。

## 补充难点 8：AT24C02 容量与设计目标的矛盾（新识别）

原始需求用 AT24C02 承载器材台账与日志，但 2KB 容量下，
假设每条日志 16 字节，仅能存约 120 条——一次实验课就可能写满。

**对策**：已通过修订 A2 解决——EEPROM 降级为配置存储，台账与日志转移到上位机。
若导师要求「必须体现本地存储能力」，可选加装 W25Q64 SPI Flash（8MB，可存约 50 万条），
届时只需重写 `drv_storage.c` 的实现，`app` 层接口不变（见 `04` 第 2.2 节）。

**验证方式**：记录实际配置区占用字节数与剩余空间，写入论文作为选型依据。

---

## 补充难点 9：三端协议不一致导致联调困难（新识别）

**成因**：STM32 用 C 手写字节序拼装，Java 用 `ByteBuffer`，前端用 JSON。
任何一端的字段偏移算错，都会表现为「数据收得到但解析乱码」，极难定位。

**对策**

1. `02-系统架构与通信协议.md` 作为唯一契约，改协议先改文档。
2. Java 侧写一个 `FrameCodecTest` 单元测试，用**手工构造的十六进制串**做输入，
   验证解码结果。这串数据同时贴进文档，STM32 侧也用同一串做自测。
3. 串口打印 STM32 发送的原始十六进制字节，与 Java 侧收到的字节直接比对，
   一眼就能定位是哪一端拼错了。
4. 新增字段用 TLV（见协议文档第 4 节），避免改偏移量引发连锁错误。

**验证方式**：固定一组十六进制测试向量，三端分别解析，结果必须完全一致。

---

## 补充难点 10：演示现场的稳定性风险（新识别）

答辩现场 WiFi 环境未知，若断网则所有远程功能无法展示。

**对策**

1. **本地功能独立可用**。OLED 显示、按键菜单、声光提示、本地日志翻页
   全部不依赖网络，断网时系统仍可完整演示借还流程。
2. **准备离线演示方案**。用手机热点替代实验室 WiFi，提前测通；
   或用两台电脑直连（网线/热点）跑通 TCP 链路。
3. **准备录屏**。将完整流程录屏作为兜底，现场出问题时可直接播放。
4. **准备模拟数据**。Java 端内置一个「模拟下位机」开关，
   不接硬件也能演示上位机全部功能。

**验证方式**：正式答辩前，在答辩教室实地演练一次，使用手机热点跑通全流程。
